## 0. 한 줄 요약

1·2차 감사가 「계산이 어긋나는 자리」를 찾았다면, 이번엔 **검증 방법 자체를 바꿔서** 찾았다.
문서의 문장만 읽고 종이에 답을 계산한 뒤 코드와 대조했고, 앱 밖에서 온 값(거래소가 스스로 적은 숫자)을
새로 찾아 붙였다. 그 결과 **수수료 자산 칸이 비어 있으면 코인이 사라지고**,
**필수 고지 문구가 PDF에서 문장 중간에 잘리고**, **CSV가 화면과 다른 숫자를 적는다**는 것을 확인했다.

동시에, 지금까지 한 번도 실데이터로 돌려 본 적 없던 **2027 과세 경로가 손 계산과 1원까지 일치**한다는 것도
처음으로 증명했다.

---

## 1. 이번 감사의 방법 — 왜 세 번이나 새 결함이 나왔는가

지금까지의 검증은 **우리 코드가 우리 코드를 검사**하는 구조였다.
엔진과 검증기를 같은 생각으로 짜면 둘이 같은 오해를 공유하고 사이좋게 통과한다.
그래서 이번에는 근거를 세 층으로 나누고, **아래 두 층을 새로 만들었다.**

| 층 | 근거 | 이번에 한 일 |
|----|------|--------------|
| 1층 (가장 강함) | **앱 밖에서 온 값** — 거래소가 원본에 직접 적어준 숫자 | 바이낸스에도 외부 근거가 있다는 것을 발견 (§4) |
| 2층 | **손으로 계산한 값** — 문서 문장만 읽고 종이에 계산 | 2027 경로·경계값·의제 두 방식을 새로 작성 (§3) |
| 3층 (가장 약함) | 코드가 코드를 검사 (검증기·무작위 시나리오) | 기존에 충분히 있었음. 자기검사 구멍 2곳 발견 (§6) |

**중요한 규칙:** 2층을 만들 때 코드를 보고 기대값을 만들지 않았다.
문서(`03-tax-rules` · `05-decisions` · `IMPLEMENTATION`)의 문장 → 종이 계산 → 테스트 단정값 순서로 작성했다.
순서가 반대가 되면 「지금 동작을 정답으로 박아 놓는」 같은 함정에 다시 빠진다.

## 2. 확인된 결함

전부 **재현 테스트로 증명**했다. 아직 고치지 않았다.

### D-1 (Critical) 원화 수수료 숫자만큼 코인이 사라진다

- 위치: `CostBasisEngine.feeCostKRW` — `let asset = e.feeAsset ?? e.baseAsset`
- 원인: 수수료 금액은 있는데 **어느 자산으로 냈는지 칸이 비어 있으면** 「기초자산으로 냈겠지」라고 넘겨짚는다.
  그 파일의 수수료가 원화 금액이면 **그 숫자만큼 코인을 처분**한다.
- 재현: 코인 10,000개를 사고 1,000개를 팔면서 수수료 1,500(원)을 적으면 → 남는 수량이 9,000이 아니라 **7,500**.
- 도달 경로: 제네릭 열 매핑(`generic-tabular-v1`)에 `fee` 열만 있고 `fee coin` 열이 없는 파일,
  바이낸스 리포트센터 CSV에서 `Fee Coin` 칸이 빈 행.
- 영향: 보유 수량과 취득원가가 동시에 틀어진다. 세액이 어느 방향으로든 크게 어긋난다.

### D-2 (Critical) 같은 조건의 매도 — 엔진과 수량 규칙이 서로 다른 답을 낸다

- 위치: `CostBasisEngine.feeCostKRW` ↔ `LedgerDelta.core` (수수료 블록이 `e.feeAsset` 이 있을 때만 돈다)
- 엔진은 기초자산을 빼고, 규칙 한 벌은 안 뺀다 → **정상 자료인데 `V-QTY-01` Critical** 이 뜨고 export 가 잠긴다.
- 재현: 엔진 보유 7.5 / 규칙 기대 8 → `V-QTY-01` critical 1건.
- 2차 감사에서 「규칙은 한 곳에만 둔다」며 `LedgerDelta` 를 만들었는데, **엔진이 그 규칙을 쓰지 않는 자리가
  한 곳 남아 있었다.**

### D-3 (Critical) 같은 조건의 매수 — 수수료가 통째로 사라진다

- 매수는 `feeCostKRW(e, skipAsset: e.baseAsset)` 로 부르므로, 넘겨짚은 자산이 기초자산이면 **0원**이 된다.
  수량도 줄지 않는다 (`if !e.quantityIsNetOfFee, let fa = e.feeAsset` 가 `nil` 에서 끊긴다).
- 재현: 같은 거래인데 수수료 자산 기재 시 취득가 1,050 / 미기재 시 1,000.
- 영향: 취득가가 작아져 **나중에 팔 때 이익이 커지고 세금을 더 낸다.**
  원본이 수수료 자산을 적었느냐는 우연에 세액이 좌우된다.

> **D-1·D-2·D-3 은 뿌리가 하나다** — 「수수료 자산이 없으면 기초자산」이라는 넘겨짚기.
> 한 곳을 고치면 셋 다 사라진다.

### D-4 (Critical) 필수 고지 문구가 PDF에서 문장 중간에 잘린다

- 위치: `ReportPDFExporter.wrap(_:width:)` + `NSString.draw(in:)`
- 원인: 줄바꿈을 **글자 수 92자**로 자른다. 한글은 고정폭 글꼴에서 영문의 약 두 배 폭이라
  종이 폭을 넘고, 그리는 영역(`CGRect`) 밖은 그대로 잘려 나간다.
- 확인: 만들어진 PDF에서 텍스트를 다시 뽑아 보면 `TaxCopy.transferCost`(88자)가
  **「… 세액이 다」에서 끊기고 뒷부분이 없다.** 주의사항 4개 중 3개도 같은 방식으로 잘렸다.
- 영향: `05-decisions §7.3` 이 **문구 그대로** 싣도록 잠근 고지가 실제로는 실리지 않는다.
  `IMPLEMENTATION §10` 의 「고지 4종이 export에 포함 (잘림 없음)」 체크가 **사실이 아니다.**

### D-5 (Critical) 「코인 바꾸기」의 낸 코인이 장부에 그대로 남는다

- 위치: `CostBasisEngine.processQuoteLeg` 의 `guard let quoteKRW else { … return }`
- 바이낸스 Transaction History 의 `Binance Convert` 는 매수(`.buy`)로 묶이고 **낸 코인이 견적자산**이 된다.
  그 코인이 스테이블이 아니면(BTC→USDT 등) 원화 환산 근거가 없어 **장부를 건드리지 않고 지나간다.**
- 재현: BTC 1개 보유 → 0.5개를 USDT로 바꿈 → 남은 BTC가 **1개**(0.5여야 함).
- 세금이 잘못 나가지는 않는다 (`V-FX-01` Critical 이 계산을 막는다). 문제는 두 가지다.
  1. **막힌 채로 사용자가 풀 방법이 없다** — 코인 간 환율을 넣는 화면이 없다.
  2. 바이낸스는 잔고 열이 없어 이 수량 오류를 `V-BAL` 로도 못 잡는다.
     (`shortfallKeys` 에 등록되어 `V-QTY-01` 도 면제된다)

### D-6 (High) OKX 매도의 총수입금액이 순액이다

- 위치: `OKXTradingHistoryCSVParser` — `feeBase` 만 읽는다 (`Fee Unit == base` 인 경우만)
- OKX 실파일 구조를 열어 확인했다: 한 주문이 **두 줄**(받는 자산 / 주는 자산)이고
  `Action` 은 주문이 아니라 **줄마다** 붙는다. 수수료는 **받는 쪽에 붙고, 그 줄의 잔고 변동은 수수료를 이미 뺀 값**이다.
- 결과: 매도에서 받은 USDT에 붙은 수수료를 파서가 아예 읽지 않아
  **양도가액이 순액**이 된다. 빗썸·바이낸스는 총액이므로 **한 신고서 안에서 기준이 갈린다.**
- 재현: 총액 1,000 USDT · 수수료 1 USDT 인 매도 → `quoteAmount` 999 · `feeAmount` 없음.
- 소득금액과 세액은 같다. 달라지는 것은 신고서의 「총수입금액」·「필요경비」 두 칸과,
  거래소 자료와 대조할 때 맞춰야 하는 금액이다 (`IMPLEMENTATION §6.4` 총액 기준 통일 · TQ-02).

### D-7 (High) CSV가 화면·PDF와 다른 자릿수를 적는다

- 위치: `ReportCSVExporter` 는 `Money.decimalString` (반올림 없음),
  화면은 `Fmt.krwString`, PDF는 `Money.roundKRW` (둘 다 원 단위 반올림)
- 재현: 같은 계산 결과에서 화면 `₩4,637,203` / CSV `4637202.9`.
- 나눗셈에서 남은 찌꺼기(소수 30자리대)까지 CSV에 그대로 나가는 경우도 확인했다.
- 영향: 신고서에 옮겨 적을 때 화면과 파일의 숫자가 다르다.

### D-8 (Medium · 잠재) 원가법 정책이 계산에 강제되지 않는다

- 위치: `CostBasisEngine` 이 `accountsByID[...]?.costMethod`(저장 값)를 쓰고
  `policies.costMethodResolver` 를 **한 번도 호출하지 않는다.**
- 재현: 저장 값이 FIFO 로 틀어진 빗썸 계정 → 정책은 이동평균(취득원가 6,000만)인데 실제로는 FIFO(4,000만)로 계산된다.
- 지금은 계정을 만들 때 올바른 값이 들어가 결과가 같다. 그러나 **「빗썸=이동평균」이라는 확정 결정이
  코드로 지켜지지 않는다** — 저장 값이 한 번 틀어지면 아무도 못 잡는다.

## 3. 손으로 계산해 확인한 것 — **문제 없음**

문서 문장만 보고 종이에 계산한 뒤 코드와 대조했다.

| 확인 | 방법 | 결과 |
|------|------|------|
| **2027 과세 경로 (실데이터)** | 실파일 5개 → 실제 보유 포지션 8종에 시가를 넣어 의제취득가 확정 → 2027년 전량 처분 → 소득금액을 손으로 재계산 | 앱과 **1원 단위까지 일치** · Critical 0건 |
| **2027 과세 경로 (합성)** | 취득단가 1,300 → 시가 1,500 → 의제 1,500 → 600만원에 매도, 수수료 1만원 | 손익 4,490,000 / 과세표준 1,990,000 / 세액 **437,800** 정확히 일치 |
| **과세 시작 경계** | 2026-12-31 23:59:59 매도 vs 2027-01-01 00:00:00 매도 | 1초 차이로 정확히 갈림 (앞은 세액 0) |
| **의제 두 방식 (TQ-01)** | 문서 §TQ-01 예시 그대로 — 4천만·8천만에 각 1개, 시가 6천만 | 평균 **1.2억** / 건별 **1.4억** — 문서 예시와 동일 |
| **다년도 · 손실 이월 없음** | 2027 −5천만 / 2028 +5천만 | 2027 세액 0 · 2028이 전 해 손실로 깎이지 않음 · 처분이 해마다 섞이지 않음 |
| **개인지갑이 과세 시작을 걸칠 때** | 2026 거래소→지갑, 2027 지갑→거래소, 그 뒤 매도 | 지갑에 있던 수량도 의제취득가를 받고, 그 값이 처분 원가가 됨 |

> 이 구간이 **지금까지 실데이터로 한 번도 돌아 본 적이 없던 최대 사각지대**였다.
> 실거래가 전부 2026년 이전이고 시가도 안 넣어서, 의제취득가 확정 → 2027 처분 → 세액 산출이
> 합성 데이터로만 돌았다. 이번에 실보유분 위에 2027 처분을 얹어 처음 통과시켰다.

## 4. 바이낸스 사각지대가 닫혔다 — 진짜 외부 정답지를 찾았다

### 문제

빗썸·OKX는 원본에 잔고가 찍혀 있어 `V-BAL` 로 자동 대조가 되는데 **바이낸스만 없었다.**
그래서 `scripts/binance-expected-balances.py` 로 잔고를 다시 계산해 대조해 왔는데,
그건 **같은 사람이 같은 규칙 이해로 짠 두 번째 구현**이라 「규칙 자체를 잘못 알았다」는 오류는
둘 다 똑같이 통과시킨다 (2차 감사 §6-5 에 한계로 적어 둔 항목).

### 찾은 것

새로 추가된 **바이낸스 Transaction History** 파일에는 계정의 **모든 잔고 변동(`Change`)** 이 적혀 있다.
이 열을 **그냥 더하기만 하면** 바이낸스가 말하는 기간 순증감이 나온다 — **우리 해석이 한 줄도 안 들어간다.**

빗썸의 「가상자산 잔고」, OKX의 `After Balance` 와 **같은 급의 외부 근거**다.

- 대조 결과: 자산 6종 전부 일치, 불일치 **0건**
- 이 파일 시작 전 보유분을 요구하는 자산도 없다 (합계가 음수인 자산 없음)

### 덧붙여 확인한 것 (서로 다른 회사가 만든 문서 2장 대조)

- `바이낸스 → OKX` 출금에 `Withdraw fee is included` 표시가 있고 OKX 입금액이 그만큼 작다
  → **출금 수량에 수수료가 포함**된다는 앱의 가정이 외부 문서로 확인됐다
- `OKX → 바이낸스` 전송의 소실률이 네트워크 수수료 범위 안

## 5. 그 밖에 확인했고 문제 없는 범위

| 영역 | 확인 방법 | 결과 |
|------|-----------|------|
| **저장·복원** | 소수 18자리·29자리 정수·음수·0 을 저장 후 재읽기 / 디스크 저장소를 닫았다 다시 열기 / 계산 스냅샷 JSON 왕복 | 값 손실 없음 |
| **수량 0 거래** | 0짜리 매수·매도를 섞어 재생 | 깨지지 않고 오탐도 없음 |
| **내보내기 잠금** | Critical 상태 · 검증 전 상태 | CSV·PDF 둘 다 거부 |
| **Decimal 정확비교** | 도메인 전체의 `==`/`!=` 지점을 훑음 | **나눗셈 결과를 정확 비교하는 자리는 남아 있지 않다.** 세액 비교는 모두 원 단위 반올림 뒤라 안전 |
| **Decimal 정밀도** | 나눗셈·재곱셈 반복, 극단 자릿수 왕복 | 오차는 유효숫자 32번째 자리 수준 — 허용 오차(1원 / 1e-10)에 영향 없음. 다만 **그 찌꺼기가 CSV로 새어 나간다** (D-7) |
| **앱 실행** | 서명 빌드 → 실행 | 정상 기동 · 크래시 없음. **화면 내용은 확인하지 못함** (이 기기에 화면 캡처 권한이 없다) |

> `Decimal(string: "1,234.5")` 가 **1** 을 돌려주는 것을 확인했다(콤마에서 끊긴다).
> 지금은 사용자 입력이 전부 `Money.parseDecimal`(콤마 제거)을 거치고 저장 문자열에는 콤마가 없어
> **안전하다.** 다만 안전한 이유가 관례뿐이라 회귀 테스트로 고정할 필요가 있다.

## 10. 남은 한계

1. **화면(UI)을 눈으로 확인하지 못했다.** 앱이 뜨고 죽지 않는 것까지만 확인했다.
   화면에 찍히는 숫자와 요약이 같은지는 계산 결과 수준에서만 대조했다.
2. **기존 저장소 마이그레이션을 실제 옛 파일로 시험하지 못했다.**
   새 필드가 전부 선언부 기본값을 갖고 있어 설계상 안전하고, 디스크 저장소를 닫았다 여는 것까지는 확인했다.
   실제로 예전 스키마로 만든 저장소 파일이 있어야 완전히 검증된다.
3. **세법 해석**은 어떤 검산으로도 정할 수 없다 (「세무 확인」 항목 참조).
4. **개인지갑 안에서 일어난 일**(지갑→지갑, 디파이)은 앱이 알 수 없다.
