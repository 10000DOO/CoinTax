## 1. Import 계층

### F-01 (Critical) CSV 줄바꿈이 `\r\n` 이면 파일 전체가 한 줄로 읽힌다

- 위치: `CoinTax/Import/Parsing/CSVUtil.swift` `parseLines`
- 원인: `Array(text)` 는 `Character` 배열이고, Swift 는 `"\r\n"` 을 **한 개의 문자**(grapheme cluster)로
  본다. 그래서 `case "\n"` 도 `case "\r"` 도 걸리지 않고 `default` 로 떨어져 줄바꿈이 필드 안에 들어간다.
- 실제 영향: 바이낸스 3개 파일(전부 CRLF) → 헤더 검증 실패, OKX 2개 파일(첫 줄만 CRLF) →
  메타행과 헤더행이 한 줄로 붙어 헤더 검증 실패. **실파일 5/5 전멸.**
- 수정: 유니코드 스칼라 단위로 순회하고 `\r\n` / `\r` / `\n` 을 모두 행 종료로 처리.

### F-02 (Critical) OKX CSV 는 모든 줄 앞에 BOM 이 붙어 있다

- 원인: 파일 전체 선두 BOM 만 제거하고 있었다. OKX 는 줄마다(그리고 메타행은 필드마다) BOM 을 넣는다.
- 영향: `id` 값 앞에 BOM 이 붙은 채 들어가 externalID·지문이 오염된다.
- 수정: `parseLines` 가 각 필드 선두의 BOM 을 제거.

### F-03 (Critical) 바이낸스 실제 CSV 포맷을 지원하지 않았다

문서(`docs/parsers/binance-*.md`)는 리포트센터 XLSX(`Date(UTC)`, `Base Asset`, `Quote Asset`, `Total`,
`Fee Coin`)만 기록했으나, 사용자가 실제로 내려받은 파일은 **거래내역 화면 CSV** 로 컬럼이 완전히 다르다.

| 파일 | 실제 헤더 |
|------|-----------|
| Spot Trade History | `Time,Pair,Side,Price,Executed,Amount,Fee` |
| Deposit History | `Time,Coin,Network,Amount,Address,TXID,Status` |
| Withdraw History | `Time,Coin,Network,Amount,Fee,Address,TXID,Status` |

Spot CSV 는 숫자에 단위가 붙어 있다 (`0.1234XAUT`, `493.6USDT`, `0.00061BNB`) 그리고
`Pair` 에 구분자가 없다 (`XAUTUSDT`).

- 수정: 세 파서가 이 변형을 함께 읽는다. base/quote 심볼은 `Pair` 를 쪼개 추측하지 않고
  `Executed`/`Amount` 의 **단위 접미사**에서 뽑는다 (`ADAUSDT` 처럼 갈라지는 지점이 모호한 쌍에서 안전).

### F-04 (Critical) 파일 시각의 타임존을 UTC 로 고정하고 있었다

- 실제 파일명: `Binance-Spot-Trade-History-202608111215**(UTC+9)**-part1-of1.csv`
- 파서는 `TimeZone(secondsFromGMT: 0)` 하드코딩 → 모든 시각이 **9시간 밀린다.**
- 영향: ① 환율 적용일이 하루 밀려 다른 날 기준환율을 쓴다 ② 연말·연초 거래가 **과세연도를 넘나든다**
  (과세 시작 시점이 2027-01-01 00:00 KST 이므로 경계 거래의 과세 여부가 뒤집힌다).
- 수정: 파일명의 `(UTC±H[:MM])` 를 우선 사용하고, 없으면 헤더 이름(`Date(UTC+0)`)에서, 그것도 없으면 UTC.

### F-05 (Critical) 빗썸 거래내역 확인서 PDF 가 **틀린 숫자로 조용히 성공**했다

- 기존 구현은 `PDFPage.string` 의 텍스트 순서에 의존했다. 이 문서는 열 단위로 그려져 있어
  텍스트 순서가 **열 우선**(모든 거래수량 → 모든 체결가격 → 모든 거래금액 …)으로 나온다.
- 결과: 95건이 들어왔지만 `매수 BTC 수량 20 / 취득가 20원` 같은 값이었다. 즉 **국내 취득원가 전체가 0 또는 쓰레기.**
  국내에서 원가가 형성되므로 이후 모든 손익·의제취득가·세액이 무의미해진다.
- 조사 결과: `PDFPage.characterBounds(at:)` 는 이 문서에서 인덱스가 어긋나 좌표를 신뢰할 수 없지만,
  `PDFDocument.findString` 과 `PDFPage.selection(for: rect)` 의 좌표·텍스트는 정확했다.
- 수정 방식 (`BithumbCertificatePDFParser`):
  1. `findString` 으로 표 머리글(`거래일시`·`자산명`·`거래금액` …)의 x·y 를 찾는다 → 하드코딩 좌표 없음
  2. 「거래일시」 열만 잘라 `selectionsByLine()` → **행 밴드**(각 거래의 y 구간)를 얻는다
  3. 행 밴드마다 전체 폭을 다시 선택 → 그 거래 한 건의 토큰만 순서대로 얻는다
  4. 토큰을 분류(날짜·시각·단위·거래구분·숫자조각)하고 **단위 토큰이 나오면 숫자 셀을 닫는다**
  5. 매매면 `[수량, 체결가격, 거래금액, 정산금액]`, 입출금이면 `[수량, 거래금액, 정산금액]` 으로 배치
  6. **교차검증**: 매매는 `|거래금액 − 수량 × 체결가격|` 이 허용 범위를 넘으면 그 행을 오류로 남기고 버린다
     (틀린 숫자를 조용히 통과시키지 않는다)
- 결과: 10페이지 **132행 전부** 정상 추출·검증 통과.

### F-06 (Warning) 빗썸 스테이킹 보상이 「미매칭 입금」으로 처리됐다

- 실데이터에 `코인 이자받기(자유형/고정형 스테이킹)` 비고가 붙은 ETH 입금 12건이 있다.
- 이건 전송 입고가 아니라 **보상 취득**이다 (`03-tax-rules.md` §8).
- 수정: 비고에 `이자받기`·`스테이킹`·`에어드랍` 이 있으면 `.income` 으로 분류 →
  전송 매칭 후보에서 빠지고 「취득가 0원」 경고가 정확한 사유로 붙는다.

### F-07 (Warning) OKX `Data migration in/out` 을 「미지원 Type」으로 버렸다

- 계정 마이그레이션 기록이며 in/out 이 같은 시각·같은 수량으로 짝을 이룬다.
- 수정: `transferInternal` 로 매핑 (합계 0, 경고 없이 정확).

## 2. 계산 엔진 · 세무 로직

### F-08 (Critical) 코인↔코인 거래에서 **견적자산(USDT) 원장이 전혀 움직이지 않았다**

- 위치: `CostBasisEngine.replay` `case .buy` / `case .sell`
- 기존 동작: `buy` 는 기초자산만 입고, `sell` 은 기초자산만 출고. **USDT 를 써서 BTC 를 사도 USDT 가 줄지 않는다.**
- 두 가지 문제가 동시에 터진다.
  1. **원장 붕괴** — 실데이터에서 바이낸스로 USDT 가 입금되고 그 돈으로 BTC·ETH·XAUT 를 사는데,
     USDT 잔고가 입금 합계 그대로 남는다. 보유 화면·평단·의제취득가가 모두 틀린다.
  2. **과세 누락** — 소득세법 시행령 제88조는 가상자산 **교환**의 양도가액 산정 방법을 규정한다.
     즉 코인↔코인 교환은 처분이다. 문서(`03-tax-rules.md` §3.1)도 `ALT→USDT` 는 처분으로 잡고 있었는데
     반대 방향 `USDT→ALT` 의 USDT 처분만 빠져 있었다 — 대칭이 깨진 상태.
- 수정: `buy` 는 견적자산을 장부에서 출고하고 **그 처분을 손익으로 인식**, `sell` 은 받은 견적자산을
  그 시점 원화가액으로 입고. 원화(KRW) 견적은 가상자산이 아니므로 그대로 제외.
- 파급: 검증기 V-QTY-01 / V-DEM-01 의 독립 수량 재계산에도 같은 규칙을 반영했다
  (반영하지 않으면 정상 계산이 전부 Critical 로 막힌다).

### F-09 (Critical) 취득가 0원 매수를 조용히 통과시켰다

- `case .buy` 에서 원화 환산에 실패하면 `cost = 0` 으로 두고 이슈를 남기지만,
  **원화 견적인데 금액 칸이 비어 있으면** `krwFromQuote` 가 성공(0원)으로 반환해 아무 이슈도 안 남았다.
  F-05 의 빗썸 파싱 붕괴가 조용히 지나간 경로가 바로 이것이다.
- 수정: 수량이 있는 `buy` 의 취득가가 0이면 `V-COST-07` Critical.

### F-10 (Critical) 1e-8 수준의 반올림 먼지가 Critical 로 올라가 export 를 잠갔다

- 거래소는 수량을 소수 8자리로 끊는다. 내부 이동·부분 체결이 수십 건 이어지면 마지막 자리에서
  1e-8 차이가 남는다. 이건 이력 누락이 아니라 반올림이다.
- 기존 판정 기준은 `Money.qtyEpsilon = 1e-10` 하나뿐이라 실데이터에서 **정상 데이터가 Critical 4건**을 냈고,
  fail-closed 규칙에 따라 신고자료 export 가 잠겼다.
- 수정: `Money.isDustShortfall(_:of:)` — 절대(1e-8)·상대(요청 수량의 100만분의 1) 중 큰 쪽 이내면
  경고로 내리고, 그 이상만 Critical 로 남긴다.
- 수정 후 남은 Critical 2건은 **실제 이력 공백**이었다 (§5 참조).

### F-11 (Latent) `extraDeductible` · `abandonedTransferCostKRW` 가 과세연도로 잘리지 않았다

- `TaxAggregator` 는 처분만 연도로 필터하고, 전 기간 합계인 `extraDeductible` 을 그 해 소득에서 뺐다.
- 기본 정책(`abandon_lost_cost`)에서는 값이 0이라 지금은 드러나지 않지만, 예약된 `deduct_as_expense`
  정책으로 바꾸면 **다른 해 비용이 이 해 소득을 깎는다.**
- 수정: 연도별로 집계해 해당 연도 값만 사용. 검증기도 요약에 기록된 연도 값으로 대조.

## 3.1 수정 후 실데이터 결과

6개 파일을 모두 import 하고, 자동 제안된 전송 후보를 **전건 매칭**한 뒤 원장을 재생했다.

검증 방법: 같은 원본 CSV 를 **파이썬으로 따로 재생**해 엔진 결과와 대조했다.
바이낸스 4개 자산(USDT·BNB·ETH·XAUT)의 최종 잔고가 **모두 소수점까지 일치**했다.

그리고 엔진이 계산한 **빗썸 USDT 잔고**는 확인서 PDF 의 「가상자산 잔고」 마지막 값과 소수점 8자리까지 같다.
파서·원장이 둘 다 맞다는 독립 증거다.

수정 전에는 바이낸스 USDT 가 입금 합계 그대로 남아 있었다.

> 구체적 수치는 개인 재무정보라 이 문서에 적지 않는다. 재현은 `RealDataTests` 로 한다.

### 남은 Critical 2건은 진짜 데이터 공백이다

바이낸스 거래내역 export 가 특정 시점부터라, **그 이전 보유분이 자료에 없다.**
그래서 USDT 1건·BTC 1건에서 「보유보다 많은 처분」이 잡힌다.

파이썬 독립 검산에서도 **같은 시점·같은 수량**으로 음수가 났다. 엔진이 정확히 잡아낸 것이므로
메시지를 「이 계정의 거래내역이 시작되기 전 보유분이 있거나 내역 일부가 빠졌을 수 있습니다 —
더 이전 기간 원본을 함께 가져오세요」로 고쳐 사용자가 무엇을 해야 할지 알 수 있게 했다.

## 4.1 개인정보 취급 (2026-08-12 점검)

원본 파일(빗썸 확인서 PDF·거래소 CSV)에는 성명·생년월일·이메일·은행 계좌·지갑 주소가 들어 있다.
**원본은 처음부터 `.gitignore` 로 막혀 있었고 커밋된 적도 없다** (`git log --all` · `rev-list --all --objects` 확인).

다만 파서를 만들면서 **실제 값을 주석·문서·테스트 단정값에 그대로 옮겨 적은** 곳이 있었다.
원본을 막는 것만으로는 부족하다는 뜻이다. 다음과 같이 정리했다.

| 조치 | 대상 |
|------|------|
| `.gitignore` 추가 | `docs/raw/`·`/raw/`·`**/거래내역/`·`**/입출금*/`·`**/원본/` (원본을 어디에 두든 잡히게) |
| `.gitignore` 추가 | 앱이 내보낸 신고자료·`*.sqlite`/`*.store` (계산 결과에도 거래 내역이 들어 있다) |
| `.gitignore` 추가 | `CoinTaxTests/RealDataTests.swift` — 실거래 수치가 단정값으로 들어가는 로컬 전용 회귀 테스트 |
| 가짜 값으로 교체 | 파서 소스 주석 · `docs/parsers/*.md` 예시 행 · `CSVUtilTests` · 이 문서의 수치 |
| 자동 검사 추가 | `scripts/check-pii.sh` |

### `scripts/check-pii.sh`

커밋될 파일만 골라 세 가지를 본다.

1. **신원 정보** — 이메일·계좌번호·주민번호·BTC/TRON/EVM 지갑 주소를 **형태(정규식)로** 잡는다.
   특정인의 값을 스크립트에 적어두면 그 자체가 유출이므로 값을 하드코딩하지 않는다.
2. **실거래 수치 유출** — 실파일에 있는 숫자가 소스·문서로 옮겨졌는지 **대조**한다.
   뒤의 0 을 뗀 유효숫자가 6자리 이상인 소수와 9자리 이상 정수만 본다 —
   그러지 않으면 허용오차 상수(`0.0001`)까지 잡혀 경고를 아무도 안 읽게 된다.
   실파일이 없는 기기에서는 이 항목만 건너뛴다.
3. **원본 파일 추적 여부** — `*.pdf`/`*.xlsx`·`거래내역`·`입출금` 이름이 추적 목록에 있는지.

`scripts/smoke.sh` 맨 앞에서 돌고, `pre-commit` 훅으로도 걸어 두었다
(`ln -sf ../../scripts/check-pii.sh .git/hooks/pre-commit`). 해제는 `rm .git/hooks/pre-commit`.

> 남은 것: `CoinTaxUITests/*.swift` 의 `// Created by …` — Xcode 자동 생성 헤더이고
> **이미 원격 히스토리에 있다.** 지금 지워도 과거 커밋에는 남으므로 별도 판단이 필요하다.

## 5. 다음에 하면 좋은 것 (이번 범위 밖)

### 거래소 잔고 열과 대조하는 검증 (V-BAL, 권장)

빗썸 확인서에는 거래마다 **「가상자산 잔고」·「통화별 잔고」** 가 찍혀 있고, OKX Funding History 에도
`Before/After Balance` 가 있다. 지금 파서는 이 열을 버린다.

이 값과 원장 재생 결과를 매 거래마다 대조하면 **이력 공백을 즉시·정확히** 잡을 수 있다.
현재 V-QTY-01 은 「이벤트 합 == 장부」라는 **내부 정합성**만 보므로, 파일 자체가 불완전하면 통과한다.
실데이터에서 빗썸 USDT 잔고가 일치하는 것을 수동으로 확인했는데, 이걸 자동 검증으로
만들면 05-decisions §8.3 이 요구하는 「이력 공백 의심 경고」가 제대로 구현된다.

필요한 작업: `LedgerEvent` 에 잔고 필드 추가(SwiftData 스키마 변경) + 파서 3곳 + 검증 규칙 1개 + UI 노출.
