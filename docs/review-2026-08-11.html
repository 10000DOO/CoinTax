1세액이 실제로 틀어지는 계산 결함

여기 있는 항목들은 앱이 조용히 잘못된 숫자를 내놓습니다. 오류 메시지도, 경고도 없이 세액이 달라집니다. 세금이 걸린 앱에서 가장 위험한 종류의 문제입니다.

1-1

OKX 매수에서 수수료를 두 번 깎습니다

치명확정

거래소마다 "수량" 칸의 뜻이 다릅니다. 바이낸스는 수수료를 떼기 전 수량을 적고, OKX는 수수료를 떼고 실제로 지갑에 들어온 수량을 적습니다. 그런데 엔진은 두 경우를 구분하지 않고 "수량에서 수수료를 한 번 더 빼라"를 일괄 적용합니다.

근거
  • Import/Parsers/OKX/OKXTradingHistoryCSVParser.swift:97-101 — 수량은 이미 순증분(Balance Change 합계)인데 feeAmount도 함께 실어서 넘김
  • Domain/CostBasis/CostBasisEngine.swift:131-133 — qty = max(0, qty - abs(fee)) 를 조건 없이 적용
문서의 OKX 예시로 따라가 보면 
docs/samples/synthetic/okx_trading_history_sample.csv 1행
  Amount = 0.01        (주문 수량)
  Fee    = -0.00001    (수수료)
  Balance Change = 0.00999   ← 이미 수수료가 빠진 실제 증가분

파서가 만드는 이벤트 : quantity 0.00999 , feeAmount 0.00001
엔진이 장부에 쌓는 값 : 0.00999 - 0.00001 = 0.00998   ← 틀림
실제 지갑 증가분      : 0.00999
결과 보유 수량이 거래마다 조금씩 부족해집니다. 나중에 전량 매도하면 "보유보다 많이 팔았다"는 오류로 계산이 아예 멈춥니다. 보유 현황 화면의 수량·평단도 함께 틀립니다.
왜 테스트가 못 잡았나 — 테스트가 쓰는 okx_trading_sample.csv는 수수료가 0입니다. 문서 예시 파일(okx_trading_history_sample.csv)은 커밋되어 있는데도 어떤 테스트도 읽지 않습니다.
제안 — 파서 단계에서 "수량이 이미 순액인지" 여부를 표시하거나, OKX 파서는 feeAmount를 원가 계산용으로만 넘기고 수량 차감 대상에서 제외합니다.
1-2

달러 계열이 아닌 견적 자산도 달러 환율로 곱합니다

치명확정

"USDT로 값을 매긴 거래만 원/달러 환율을 쓴다"가 의도인데, 조건문이 잘못 묶여서 항상 참이 됩니다.

근거 
Domain/CostBasis/CostBasisEngine.swift:98
  if qa == nil || qa!.isUSDTish || policies.fxAssumption.usdtEqualsUSD
                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                  기본 정책에서 항상 true → 앞의 검사가 무의미

Domain/CostBasis/CostBasisEngine.swift:115-122  (매도)
  → 원화인지만 보고, 그 외에는 검사 없이 곧바로 환율을 곱합니다.
결과 ETH/BTC 처럼 BTC로 값을 매긴 거래에서 "BTC 수량 × 원/달러 환율"이라는 의미 없는 금액이 취득가·양도가로 들어갑니다. 예를 들어 0.5 BTC를 지불한 거래가 "0.5 × 1,400 = 700원"으로 계산됩니다.
문서와의 관계 — docs/IMPLEMENTATION.md:148은 이 경우를 "환산 불가 → needsFX / 누락 처리"로 잠가 놨습니다. 그 누락 처리 코드는 CostBasisEngine.swift:105-106에 있지만 절대 실행되지 않는 죽은 코드입니다.
제안 — usdtEqualsUSD 조건을 || 에서 빼고, USDT/USD/원화 이외의 견적 자산은 문서대로 누락 처리합니다.
1-3

OKX 파일 두 개를 같이 넣으면 거래소 내부 이동이 이중으로 반영됩니다

치명확정

OKX는 "펀딩 지갑 ↔ 거래 지갑" 사이의 내부 이동을 두 파일에 각각 기록합니다. 그런데 앱은 같은 이동을 파일에 따라 다르게 해석합니다. 문서는 두 파일을 모두 넣으라고 안내합니다(docs/04-import-formats.md:168).

파일같은 이동을 어떻게 보는가장부에 벌어지는 일
Funding History 내부 이동 transferInternal 아무 일도 안 함 (정상)
CostBasisEngine.swift:220-222
Trading History 외부 입금 / 출금 deposit·withdrawal 입금 방향: 원가 0원으로 수량이 늘어남
출금 방향: 원가가 소멸 처리됨
OKXTradingHistoryCSVParser.swift:53
결과 내부에서 돈을 옮긴 적밖에 없는데도 공짜로 코인이 생기거나(원가 0), 취득원가가 사라집니다. 두 파일을 다 넣은 사용자는 세액이 위아래로 크게 흔들립니다.
문서도 알고 있었음 — docs/parsers/okx-funding-history.md:82 "동일 이동이 양쪽에 비슷하게 찍히면 dedupe / 링크 필요할 수 있음". 구현은 없습니다.
제안 — Trading History의 Transfer 행은 시간·수량·자산으로 Funding 쪽 내부 이동과 대조해 제거하거나, 기본적으로 transferInternal로 해석하고 외부 입출금은 Funding 파일만 신뢰합니다.

근거
  • Infrastructure/FX/ECOSFXClient.swift:97-111 — 공개 API 클라이언트가 값을 못 찾으면 내부적으로 최대 10일 과거로 되짚어 찾은 뒤, 그 값을 요청한 날짜 키로 반환
  • Infrastructure/FX/ECOSFXClient.swift:153-159 — 합성 클라이언트도 직전 값으로 채워 같은 키로 반환

제안 — 원격 클라이언트가 되짚기를 하지 말고 있는 날짜만 반환하게 하고, 되짚기는 FXHolidayPolicy 한 곳에서만 하게 합니다. 저장 시 sourceDate는 항상 실제 고시일을 씁니다.

빗썸 실제 PDF는 사실상 파싱되지 않습니다

치명확정

빗썸은 거래내역을 PDF로만 제공하고, 그 PDF는 금액 줄 아래에 단위 줄(USDT/KRW)이 붙는 2단 구조입니다. 날짜와 시간도 두 줄로 나뉠 수 있습니다. 문서는 "줄 병합이 필요하다"를 세 곳에서 강조합니다.

근거
  • Import/Parsers/Bithumb/BithumbCertificatePDFParser.swift:56-83 — 병합 로직이 없습니다. 한 줄에 모든 칸이 있다고 가정한 정규식 1개 + 파이프(|) 구분 텍스트 처리만 존재
  • 문서 요구: docs/parsers/bithumb-transaction-certificate.md:43,106 · docs/design/09-import-and-matching.md:83 · docs/design/14-implementation-spec.md:355
결과 실제 확인서를 넣으면 0건이 추출되고, 그것도 오류가 아니라 경고 한 줄로 조용히 "성공" 처리됩니다 (:85-87). 사용자는 가져온 줄 알고 다음 단계로 넘어갑니다. 국내 거래 전체가 빠진 상태로 세액이 계산됩니다.
MVP 체크리스트와의 관계 — docs/01-requirements.md:272의 "빗썸 PDF import 가능 [x]"는 합성 텍스트 파일에서만 참입니다.
제안 — (a) 줄 병합 단계를 추가하고, (b) 추출 0건은 E_PARSE_ROW 오류로 올리고, (c) 실제 레이아웃을 재현한 미니 PDF fixture를 테스트에 넣습니다.

  • Application/CalculationPipeline.swift:46 — 그대로 상위로 전파 → 화면엔 짧은 에러 문구만

3검증(Verify)이 약속의 절반도 안 됩니다

이 앱의 안전장치는 "계산이 끝나면 독립적으로 다시 검사해서, 통과 못 하면 내보내기를 막는다"입니다. 그런데 그 검사 목록이 문서가 못박은 것의 절반도 구현되지 않았습니다. 1장의 결함들이 전부 이 안전장치가 잡아야 했던 것이라는 점이 핵심입니다.

3-1

문서는 20개 이상을 필수로 못박았고, 구현된 것은 9개입니다

높음확정

게다가 두 개의 "확정" 문서가 서로 다른 약속을 하고 있습니다. docs/06-integrity.md:60-126은 20개 이상을 "v1 Must · Critical"로, docs/design/14-implementation-spec.md:557은 9개를 "최소 구현"으로 적었습니다. 코드는 느슨한 쪽만 따릅니다(Domain/Integrity/Verifier.swift).

그 외 검증 관련 문제
  • 감사 추적 필드가 아예 없습니다. 문서(docs/06-integrity.md:49)는 실현 건마다 "lot 스냅샷 id, 환율 id, 의제 적용 여부"를 요구하는데 Domain/Models/TaxModels.swift:3-16의 DisposalRecord에 없습니다. 그래서 V-FX-02는 만들 수조차 없습니다.

8추가 검토 · 자료조사가 필요한 항목

여기는 "코드가 틀렸다"가 아니라, 판단 근거가 문서에 없어서 지금의 결정이 맞는지 확인할 수 없는 항목들입니다. 세법·외부 API 확인이 선행되어야 합니다.

8-1

의제취득가를 "묶어서" 비교하는지 "매입 건별"로 비교하는지 — 세액 차이가 큽니다

자료조사

현재는 계정×자산의 평균 단가와 시가를 비교합니다 (Domain/CostBasis/CostBasisEngine.swift:243-248). 선입선출 계정이라면 매입 건(lot)별로 비교하는 것이 자연스러울 수 있습니다.

예: 1 BTC를 4천만원에, 1 BTC를 8천만원에 산 뒤 시가가 6천만원일 때
방식계산의제 취득가 합계세금 방향
평균 비교 (현재 코드)max(평균 6천, 시가 6천) × 21억 2천만원—
건별 비교max(4천, 6천) + max(8천, 6천)1억 4천만원취득가 2천만원 ↑
결과 현재 방식이 취득가를 2천만원 적게 잡아 세금이 더 나옵니다. 문서 어디에도 이 선택에 대한 논의가 없습니다 (docs/05-decisions.md:229-261, docs/design/07-tax-deemed-holdings.md). 법령·국세청 안내 확인이 필요합니다.
8-2

의제 "시가"의 정의와 출처 표기

자료조사

법령은 시가고시 사업자들의 공시가격 평균 등으로 정의합니다. 앱은 사용자가 자산별로 값 하나를 직접 입력하는 방식이고 (Features/Settings/SettingsView.swift:103-113), 문서도 "v1은 사용자/조회 시세 테이블"(docs/05-decisions.md:250)로 남겨뒀습니다. 리포트에 시가 출처가 표시되지도 않습니다(MarketPriceEntity.source는 저장만 됨).

필요한 것 신고 자료로 쓰려면 시가의 정의(기준 시각·평균 방식)와 자산별 출처 표기가 필요합니다.
8-3

세액 절사 규칙

자료조사

현재는 1원 단위 사사오입입니다(Domain/Models/Money.swift:6-11). 실제 신고·납부에서는 10원 미만 절사 등 다른 규칙이 적용될 수 있습니다. 문서도 "국세 원단위 규칙 확정 시 교체"(docs/design/01-architecture.md:143)로 열어뒀습니다. 지방소득세를 "과세표준 × 2%"로 볼지 "국세 × 10%"로 볼지도 문서에 두 가지가 병기되어 있습니다 (docs/03-tax-rules.md:56 — 현재 값은 같지만 절사 시점이 달라집니다).

8-4

환율 데이터 소스 검증 — 공개 폴백은 "기준환율"이 아닙니다

자료조사
  • 한국은행 ECOS 통계표 731Y001 / 항목 0000001이 원/달러 매매기준율인지, 응답 형식·조회 한도가 맞는지 확인이 필요합니다(Infrastructure/FX/ECOSFXClient.swift:23).
  • 키가 틀렸을 때 사용자에게 알리지 않고 조용히 공개 폴백으로 넘어갑니다(:39-44).
  • 공개 폴백(cdn.jsdelivr.net/.../currency-api)은 외국환거래법상 기준환율이 아닙니다. 코드 주석은 이를 인정하지만(:70), 저장된 값은 리포트에서 구분되지 않고 1-4 때문에 출처까지 잘못 기록됩니다.
결과 신고 자료의 환율 근거가 "공식 기준환율"인지 "참고 시세"인지 구분되지 않습니다. 문서가 요구한 "리포트: 사용 환율 출처 요약"(docs/design/08-fx-service.md:91)도 화면·export 어디에도 없습니다.
8-5

USDT 이외의 견적 자산 환산 근거

자료조사

"USDT = USD 1:1"은 문서화되어 있습니다(TaxCopy.usdtPeg). 그런데 BTC·ETH로 값을 매긴 거래를 어떻게 원화로 환산할지는 정해진 것이 없습니다 (1-2와 직결). 재정환율 준용 여부 등 정리가 필요합니다.

8-6

총수입금액의 정의가 국내/해외에서 다릅니다

자료조사
계정총수입금액으로 잡는 값수수료 처리
빗썸 매도정산금액 = 수수료 차감 후 순액이미 반영됨

8-7

사용자에게 알려야 하는데 안 알리는 것들

자료조사
  • 취득가 0원 처리 경고 없음. 에어드롭·수수료 리베이트·미매칭 입금은 취득가 0으로 처리돼 처분 시 거의 전액이 이익이 됩니다(CostBasisEngine.swift:169,226). 문서는 경고를 요구하지만(docs/03-tax-rules.md:202) 화면에 상시 노출되는 경고가 없습니다.
  • 손실 이월 불가 안내 없음. 손실이 나도 다음 해로 넘기지 못한다는 설명이 없습니다.
  • 시행 유예 가능성 안내 없음. 문서는 "시행 유예·개정 가능성 있음"(docs/03-tax-rules.md:26)이라고 적었지만 화면에는 나오지 않습니다.
  • 미매칭 출금의 원가 소멸 설명 없음. 세액을 늘리는 방향인데(CostBasisEngine.swift:207-209) 그 사실이 리포트에 설명되지 않습니다.
