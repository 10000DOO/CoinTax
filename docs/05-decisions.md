## 1. 원가 방식 — 조사 결과

### 1.1 근거 (국세청·법령)

국세청 「거주자의 가상자산소득 과세 개요」 및 소득세법 시행령 제88조 취지:

1. 기타소득금액 산출 시 **가상자산주소별**로 취득가액을 평가한다.  
2. 평가방법 구분:
   - **신고수리가상자산사업자**를 통해 거래되는 가상자산 → **이동평균법**  
     (소득세법 시행령 제92조제2항제5호 이동평균법 준용)
   - **그 외** → **선입선출법(FIFO)**
3. 소득금액 = 양도·대여 대가 − (실제 취득가액 + 부대비용)  
4. 2027-01-01 전 보유분: 취득가 = **max(실제 취득가, 2026-12-31 시가)** (의제)

참고: 일부 2024 세법개정 논의에서 **총평균법** 전환이 언급된 바 있으나, **2026-08 국세청 공개 안내는 여전히 이동평균/선입선출 이원 체계**이다. 법령이 총평균으로 바뀌면 엔진 정책만 교체한다.

### 1.2 CoinTax 적용 규칙 (확정)

| 계정 유형 | 예 | 기본 원가법 |
|-----------|-----|-------------|
| 국내 신고수리 가상자산사업자 | **빗썸** | **이동평균법** |
| 해외 거래소 (신고수리 사업자 아님) | **바이낸스, OKX** | **선입선출법** |
| 개인지갑·기타 (v1 비주력) | — | 선입선출법 |

- 단위: **계정(=가상자산주소 대리)** × **자산 심볼** 별로 원장 분리.  
- **전송(입출금)**: 양도로 보지 않고, 출고 원가를 도착 계정 입고 원가로 **이전**.  
  - 출고 측: 해당 계정 원가법으로 출고 단가 산출  
  - 입고 측: 이전된 KRW 원가·수량으로 lot/평균 갱신  
  - **수수료 소실**: §7 보수 정책  
- 리포트에 계정별 적용 방법 명시.

### 1.3 왜 “전역 단일 방법”이 아닌가

국내(빗썸)와 해외(바이낸스/OKX)를 동시에 쓰는 사용자 플로우가 제품 핵심이므로, 법령의 **주소(사업자)별 이원 적용**을 그대로 따른다.

## 3. 환율 — 조사 결과 및 자동화 설계

### 3.1 과세에서 쓰는 환율

국세청 안내 · 소득세법 시행령 제88조 교환거래 관련:

- 외국통화에 연동되는 기축가상자산(예: **USDT**) 가액  
  → **「외국환거래법」 제5조에 따른 기준환율 또는 재정환율**로 환산  
- 시가고시 국내 사업자 KRW 마켓 거래: 해당 **금전 교환 가액(KRW)** 우선

실무적으로 일별 **매매기준율(기준환율)** 은 **서울외국환중개**가 고시하는 시세가 널리 쓰이며, 한국은행·각종 공공 데이터로 동일 계열 수치를 조회할 수 있다.

### 3.2 CoinTax 환율 정책 (확정)

| 우선순위 | 소스 | 동작 |
|----------|------|------|
| 1 | 거래 행에 **이미 KRW** 금액이 있음 (빗썸 KRW 마켓) | 그대로 사용, 환율 불필요 |
| 2 | **자동**: 거래일(KST 기준 일자)의 **USD/KRW 기준환율** | 공개 일별 시세 조회 후 캐시 (로컬 DB) |
| 3 | 자동 실패·휴일·누락 | **필요 날짜 목록** UI 제시 → 사용자 수동 입력 또는 CSV import |
| 4 | 수동 환율표 파일 | `date, currency, rate` 일괄 import |

**USDT 취급 (v1):**  
USDT는 USD 연동 스테이블로 보고 **USDT 1 = USD 1** 가정 후, 해당일 **USD 기준환율**로 KRW 환산. (페그 이탈 구간은 수동 보정 여지를 설정에 남김)

**다른 외화 견적** (드묾): 재정환율 또는 USD 경유 환산 — v1은 USD 중심.

### 3.3 자동화 구현 방향

```text
계산 시 필요 일자 집합 N = { 해외 처분·취득 등 KRW 환산이 필요한 거래의 날짜 }
  → 로컬 FX 캐시에 있는 날짜 제외
  → 부족분: 공개 일별 기준환율 조회 시도 (사용자 동의 시에만 네트워크)
  → 여전히 부족: MissingFXDates 리스트 → 수동 입력 화면
  → 전부 채워진 뒤에만 TaxYearSummary 확정 계산 (또는 경고 포함 부분 계산 옵션)
```

**네트워크 정책 (개인 로컬 앱):**

- 기본: **오프라인 가능**. 환율 자동 조회는 명시적 「환율 채우기」 액션 또는 설정 옵트인.
- 조회 결과는 **로컬 캐시만** 저장. 거래 원본을 외부로 보내지 않음 (날짜·통화쌍만 요청).

**후보 데이터 소스 (구현 시 1개 확정):**

| 소스 | 비고 |
|------|------|
| 한국은행 ECOS 등 공개 API | 일별 환율 시계열, 자동화에 유리 |
| 서울외국환중개 고시 시세 | 기준환율 원천에 가깝지만 스크래핑 취약 |
| 사용자 CSV (서울외환/은행 다운로드) | 완전 오프라인 폴백 |

휴일: 해당일 미고시 시 **직전 영업일 기준환율** 사용 규칙을 설정으로 두고, 리포트에 “적용 일자”를 기록한다.

### 3.4 수동 입력이 필요할 때 UI

사용자에게 보여주는 정보:

- 날짜 (YYYY-MM-DD)  
- 통화쌍 (USD/KRW)  
- 용도 건수 (해당일 거래 N건)  
- 입력 필드: 기준환율  

입력 후 재계산.

## 7. 전송 수수료 — 보수 정책 (확정)

### 7.1 상황

```text
출금 10 USDT (원가 14,000원/USDT = 140,000원)
네트워크 수수료 1 USDT 소각
입금  9 USDT
```

### 7.2 선택지와 세금 방향

| 방식 | 입고 원가 | 이후 매도 시 | 세금 방향 |
|------|-----------|--------------|-----------|
| A. 소실 원가를 입고에 안분 | 140,000÷9 | 취득가↑ → 이익↓ | 세금 낮아질 수 있음 |
| B. 소실 원가를 “비용”으로 즉시 공제 + 입고는 9/10만 | 이중 해석 위험 | 공제 과다 가능 | 위험 |
| C. **보수 (채택)** | 입고 = 출고원가 × (9/10) 만 이전, **소실 1 USDT 분 원가 140,000×0.1 은 폐기(공제 안 함)** | 취득가↓ → 이익↑ 가능 | **세금 다소↑, 과소신고 리스크↓** |

### 7.3 채택: C (세금 문제 최소화 우선) + 교체 가능

사용자 요청: *“약간 더 많이 내더라도 세금 문제가 안 생기게.”*  
고지·교체 설계 요청: 세법 해설 공백을 명시하고, 확정 시 바꾸기 쉽게.

**고정 고지 문구 (`TaxCopy.transferCost`):**

> 전송 소실 원가는 공개 세법 해설이 없어, 과다 공제를 피하기 위해 필요경비·도착 취득가에 넣지 않습니다. 세액이 다소 커질 수 있으며 세무 자문이 아닙니다.

**규칙 (policy id = `abandon_lost_cost`):**

1. 전송은 양도(실현)로 잡지 않는다.  
2. `transferredCost = outboundCost × (receivedQty / withdrawnQty)` 만 입고.  
3. 소실 분 원가·별도 출금 수수료 원가 = **필요경비 미산입·도착 취득가 미산입**.  
4. 리포트에 `transferCostAbandonedKRW` 참고 표시 + 위 고지.  
5. 매수/매도 **체결** 수수료는 기존 취득가 가산·양도가 차감.

**교체 용이성:** 엔진은 `TransferCostPolicy` 프로토콜만 의존.  
예약 구현: `allocate_to_arrival`, `deduct_as_expense` (default 아님).  
세법 확정 시 구현체·`PolicyBundle` id·고지 문구·Verifier 분기만 교체.  
→ [design/04-policies.md](./design/04-policies.md), [design/13-testing-roadmap.md](./design/13-testing-roadmap.md) §4.

## 8. 의제 취득가 — 이력 자동 (확정)

```text
의제취득단가(자산, 계정) = max( 2026-12-31 시점 장부 실제원가, 2026-12-31 시가 )
보유수량·원가는 “과거 전 거래 재생”으로 산출
```

### 8.1 사용자 할 일

1. **과세 시행 전·후를 포함한 가능한 한 모든** 거래 CSV import  
2. 전송 매칭 확정  
3. 환율 채움  
4. (필요 시) **2026-12-31 시가** — 자동 조회 실패 분만 입력  

**별도 “의제 취득가 수동 표”를 기본 UX로 두지 않는다.**  
시가만 외부 입력이고, **실제 취득가·보유 수량·max 적용은 엔진이 판단**.

### 8.2 엔진 절차

1. 전체 이벤트를 시간순 재생 → **2026-12-31 24:00(KST) 스냅샷**  
   - 계정×자산: 수량, 실제 장부 원가(총액·평단)  
2. 동일 시점 **시가** 확보 (시가고시 평균 취지; v1은 사용자/조회 시세 테이블)  
3. 각 포지션:  
   - `deemedUnit = max(bookUnitCost, marketUnitPrice)`  
   - `deemedTotal = deemedUnit × qty`  
4. **2027-01-01 0시** 이후 원장을 의제 원가로 **리셋(재기동)** 한 뒤 이후 거래 재생  
5. 리포트에 포지션별: 실제원가 / 시가 / 채택값 / 채택 사유(`actual` \| `market`)

### 8.3 전제·경고

- 이력이 빠지면 실제원가·수량이 틀리고 의제도 틀린다 → **정합성 검증 + “이력 공백 의심” 경고** 필수.  
- 시가 없는 자산은 의제 확정 불가 → 계산 상태 `blocked` 또는 실제원가만 쓰는 **명시적 위험 모드**(기본은 차단).

## 10. 정합성 검증 (확정, 최우선)
