> **이 문서의 용도.** 아래 「프롬프트」 절 전체를 복사해 **새 AI 세션에 붙여 넣으면 된다.**
> 앞선 감사 6회에서 실제로 결함을 잡아낸 경로만 추려 규칙으로 굳힌 것이다.
>
> **왜 필요한가.** 내가 짠 코드를 내가 짠 테스트로 검사하면, 코드와 테스트가 같은 오해를
> 공유할 때 사이좋게 통과한다. 이 저장소는 그 이유로 여섯 번 감사했고 **매번 새 결함이
> 나왔다.** 이 프롬프트는 그 우회를 강제한다 — **정답을 코드 밖에서 가져오게** 만든다.

> 범위를 좁히고 싶으면 프롬프트 3장의 우선순위 1~3번(총평균법 엔진 · 50% 의제 · Trezor
> 파서)만 지정하면 된다. 가장 새 코드라 결함이 있다면 거기 있을 확률이 가장 높다.

# CoinTax 결함 사냥 — 기존 테스트를 믿지 말고 처음부터 다시 의심하라

## 0. 이 일의 성격

이 저장소는 **한국 가상자산 과세(2027-01-01 시행) 신고용 세액 계산기**다.
숫자가 틀리면 사용자가 국세청에 잘못된 금액을 신고한다. 정확성이 전부다.

너의 임무는 **결함을 찾는 것**이지 결함을 찾았다고 보고하는 것이 아니다.
없으면 "이 범위는 이런 방법으로 확인했고 문제 없음"이 정답이다.
**보고를 위해 억지 근거를 붙이거나 없는 결함을 만들면 그 자체가 최악의 실패다.**

**시간과 토큰은 신경 쓰지 마라.** 오래 걸려도 되고 많이 읽어도 된다. 손계산을 끝까지
해도 되고, 테스트를 몇 번을 돌려도 되고, 확신이 설 때까지 원문을 다시 봐도 된다.
빨리 끝내려고 검증을 건너뛰는 것이 유일하게 금지된 절약이다. **정확도가 유일한 기준이다.**

**빈손으로 끝내도 된다.** 결함이 0건이면 0건이라고 보고하라. 그건 실패가 아니라
유효한 결과다. "무언가는 찾아야 한다"는 압박에서 나온 보고 — 근거 없는 「의심스럽다」,
스타일 지적을 결함으로 부풀린 것, 4장의 미결을 결함으로 둔갑시킨 것 — 은
아무것도 못 찾은 것보다 나쁘다. **틀린 결함 1건이 놓친 결함 1건보다 해롭다.**
사용자가 그걸 믿고 맞는 코드를 고치기 때문이다.

## 1. 왜 기존 테스트를 믿으면 안 되는가 (반드시 먼저 읽어라)

이 저장소는 지금까지 여섯 번 감사했고 **매번 새 결함이 나왔다.** 원인은 게으름이 아니라 구조다.

1. **검증기가 자기 자신을 검사했다.** 계산 엔진과 검증 규칙을 같은 사람이 같은 생각으로 짜서,
   둘이 같은 오해를 공유하면 사이좋게 통과했다.
2. **테스트가 현재 동작을 정답으로 박아 놨다.** 코드를 고칠 때 테스트도 같이 고쳐야 했는데,
   그건 그 테스트가 **틀린 숫자를 정답이라고 단언하고 있었다**는 뜻이다.
3. **「실패할 수 없는 검사」가 있었다.** 예: `A = B + C` 로 만든 값을 다시 `B + C` 와 비교.
   검사 항목이 하나 있는 것처럼 보이지만 아무것도 검사하지 않는다.

**직전 회차 실측**: 결함 9건이 나왔는데 그중 **8건은 전체 테스트가 통과하는 상태**에서 나왔다.

> **테스트 전부 초록불 = "코드가 코드대로 돈다"이지 "숫자가 맞다"가 아니다.**

그러니 이렇게 하라.

- 기존 테스트의 **단정값(expected)을 증거로 쓰지 마라.** "이 값이 왜 정답인가"를
  법령·원본자료·손계산으로 **독립적으로 다시 유도**하라. 유도가 안 되면 그게 결함 후보다.
- `XCTAssert*` 옆 주석에 적힌 설명을 사실로 받아들이지 마라. 주석도 같은 사람이 썼다.
- 테스트를 고쳐야 한다면 **왜 그 단정값이 틀렸는지 근거를 대고** 고쳐라.

## 2. 결함을 잡는 다섯 가지 무기 (직전 회차에 실제로 통한 것)

기존 테스트를 우회하는 유일한 방법은 **코드 밖에 있는 정답**을 가져오는 것이다.

### 무기 1 — 법령 원문 (도메인 정답지)

세법 백서 `docs/00-tax-law-ssot.md` 가 이 저장소의 세법 단일 진실 공급원이다.
**그러나 그것도 사람이 쓴 것이다.** 원문으로 다시 대조하라.

전역 MCP 두 개가 붙어 있다 (`claude mcp list` 로 확인). 셸로도 된다:

```bash
export LAW_OC=test
korean-law search_law --query "소득세법 시행령"        # MST 획득
korean-law get_law_text --mst <MST> --jo "제88조" --efYd 20270101
korean-law search_admin_rule --query "..." && korean-law get_admin_rule --id <id>
```

**함정**: 가상자산 조문은 대부분 **2027-01-01 시행예정**이라 현행 본문을 조회하면
"그런 조문 없음"이 나온다. 반드시 `--efYd 20270101` 을 붙여라.
(현행 소득세법 시행령 제88조는 `삭제` 상태다.)

확인할 것: 조·항·호 번호, 숫자(세율·금액·기한), **시행일**, 그리고 **부칙**.
부칙의 시행일·적용례·경과조치는 **서로 다른 규정**이다. 직전 회차에 이 셋을 섞어 적은 결함이 있었다.

### 무기 2 — 구현과 무관하게 성립해야 하는 성질 (메타모픽/보존)

구현을 몰라도 성립해야 하는 등식을 **엔진 밖에서** 세우고 무작위 시나리오로 두들겨라.
직전 회차에 결함 4건이 여기서 나왔다.

이미 있는 것: `CoinTaxTests/CostConservationTests.swift`(원가 보존),
`PropertyTests`/`PropertyWideTests`(무작위+변이).

**새로 세울 성질을 직접 발명하라.** 예시(그대로 쓰지 말고 더 찾아라):

- **보존**: 들어온 돈 = 나간 돈 (처분 원가 + 소멸 + 남은 장부). 원본 이벤트에서 직접 센다.
- **순서 무관**: 총평균법에서 **판 순서를 바꿔도 그해 세액이 같아야** 한다.
- **결정성**: 같은 입력을 두 번 돌리면 **마지막 자리까지** 같아야 한다.
  (직전 회차: 딕셔너리 순회 순서로 소수를 더해 실행마다 세액이 달랐다.)
- **분할 불변**: 한 건을 두 건으로 쪼개도(수량·금액 합 동일) 세액이 같아야 한다.
- **계정 재배치 불변**: `[영]` §88① 이 거주자별이므로, **같은 코인을 어느 계정에 두든**
  그해 세액이 같아야 한다. 계정만 바꿔서 두 번 돌려 비교하라.
- **연도 경계**: 2026-12-31 23:59 KST 와 2027-01-01 00:00 KST 처분의 귀속이 갈리는가.
  타임존을 UTC 로 잘못 읽으면 하루가 밀린다.
- **단조성**: 양도가액을 올리면 세액이 줄지 않아야 한다.
- **0/음수/극단**: 수량 0, 손실만 난 해, 18자리 소수, 한 자산 전량 소진.

### 무기 3 — 일부러 망가뜨리기 (변이 테스트)

**"이 검사는 진짜로 잡는가"를 확인하는 유일한 방법.**
계산 코드 한 줄을 의도적으로 틀리게 바꾸고 테스트를 돌려라. **아무것도 안 깨지면
그 자리에 그물 구멍이 있는 것이다.**

최소한 이 변이는 해 보라:
- 총평균 단가 계산에서 기초 재고를 빼먹기
- 기본공제 250만 → 200만
- 끝수 버림 → 반올림
- 소실 원가를 필요경비에 넣기
- 처분 원가에 수수료를 두 번 더하기
- 과세연도 경계를 UTC 로 판정하기

깨지지 않는 변이를 찾으면 **그게 결함 보고다**(검출 공백). 변이는 반드시 되돌려라.

### 무기 4 — 실제로 실행해 보기

빌드·테스트가 **절대 보지 않는 층**이 있다.

```bash
./scripts/smoke.sh          # PII 검사 + 빌드 + 전체 테스트 (이걸로 돌려라)
# UI 는 직접 띄워라
xcodebuild -scheme CoinTax -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath /tmp/dd -configuration Debug \
  CODE_SIGNING_ALLOWED=NO CODE_SIGN_IDENTITY="" build
codesign --force --deep --sign - /tmp/dd/Build/Products/Debug/CoinTax.app
open /tmp/dd/Build/Products/Debug/CoinTax.app
screencapture -x -o /tmp/ui.png   # 찍어서 눈으로 봐라
```

직전 회차에 이 방법으로 **"2,026년 예상 세액"**(연도에 천 단위 쉼표)을 잡았다.
SwiftUI 의 `Text("\(정수)")` 는 로캘 숫자 형식을 적용한다. 빌드도 되고 344개 테스트도
전부 통과하며 **화면에서만 보인다.**

같은 눈으로 볼 것: 화면 ↔ PDF ↔ CSV 의 숫자가 같은가, 신고서에 옮겨 적을 값이
파일에 다 있는가, 0원·손실·빈 프로젝트 같은 경계 상태에서 화면이 무엇을 말하는가.

### 무기 5 — 문서와 코드가 같은 말을 하는가

**둘이 다르면 하나는 틀렸다.** 그리고 사용자는 화면 문구를 믿는다.

대조할 것:
- `docs/00-tax-law-ssot.md`(세법) ↔ `Domain/Policies/*`(정책) ↔ 실제 계산 결과
- `Domain/Policies/TaxOpenQuestions.swift`(「세무 확인」 28건)의 `currentAssumption` 이
  **코드가 실제로 하는 일과 같은가**
- `TaxCopy` 의 고지 문구가 폐지된 규정을 말하고 있지 않은가
- 백서 13장(코드 영향 목록)의 상태가 실제와 맞는가

직전 회차에 코드는 총평균법으로 계산하는데 화면은 "빗썸은 이동평균법을 씁니다"라고
말하고 있었다.

## 3. 우선 파고들 자리 (직전 회차 기준 위험도 순)

1. **거주자별 총평균법 엔진** — 이번에 통째로 갈아엎었다. 가장 새 코드이고 가장 위험하다.
   `Domain/CostBasis/ResidentCostPool.swift`, `CostBasisEngine.swift`
   특히: 연도 이월, 의제취득가 재기동과의 결합, 수수료 원가 수렴, 수량 부족 시 배분,
   소실(폐기) 처리, 계정 장부와 풀의 수량 일치.
2. **필요경비 의제 50%** (`[법]` §37⑥) — 이번에 새로 넣었다.
   자산별 일괄인가, 부대비용이 정말 빠지는가, 켰다 껐다 할 때 값이 일관된가.
3. **Trezor 지갑 파서** — 이번에 새로 넣었다. 방향 판정(`Address` 열)이 핵심이다.
   내 지갑 주소를 못 찾는 파일, 한 트랜잭션에 3행 이상, 금액 0 + 수수료만.
4. **끝수 계산** — 과세표준 1원 버림 / 국세·지방세 **각각** 10원 버림.
   합쳐서 절사하면 틀린다. 경계값(9원, 10원, 11원)을 두들겨라.
5. **전송 연결과 원가 이전** — 자기 계정 간 이동에서 원가가 새거나 두 번 잡히지 않는가.
6. **실데이터 전 구간** — `docs/samples/raw/` (빗썸 PDF·바이낸스 CSV·OKX CSV·Trezor CSV).
   `scripts/binance-expected-balances.py` 로 만드는 **바이낸스 잔고 정답지**는 앱 밖에서 온
   유일한 외부 정답지다. **그 파일이 없으면 검증이 조용히 skip 된다** — 반드시 먼저 생성하라.
7. **저장·복원** — SwiftData 왕복, 스냅샷 JSON 왕복에서 Decimal 이 깨지지 않는가.

## 4. 이미 알고 있는 미결 (여기서 "결함"을 만들지 마라)

아래는 **법에 답이 없어서** 앱이 가정을 세운 자리다. 2026년 10월 국세청 고시 대기 중이며,
백서 11.1 에 목록이 있다. **가정이 명시되고 사용자에게 고지되고 정책 교체가 가능하면 정상이다.**

- 디파이 예치·인출을 양도로 볼지 (U-05) / 대여(Earn·렌딩) 소득 계산 (U-06)
- 스테이킹·에어드롭·하드포크·채굴 (U-01~U-04)
- 「거주자별」 합산 범위 (U-08) / 의제취득가와 총평균법의 결합 (U-09)
- 전송 수수료 소실분의 원가 (U-10) / 가스비 범위 (U-11)
- 의제 50%의 요건-효과 범위 불일치 (U-24)

**단, 다음은 진짜 결함이다**: 가정을 세워 놓고 **고지하지 않은 것**,
문서가 정한 결정과 **코드가 다른 것**, 미결을 **확정인 것처럼** 표시한 것.

## 5. 절대 규칙

- **개인정보**: `docs/samples/raw/` 의 실제 수치(수량·주소·TXID·이름·UID)를 소스·문서·커밋
  메시지에 **절대 옮겨 적지 마라.** 대화로 보고하는 건 괜찮다.
  실데이터 단정값은 `CoinTaxTests/RealDataTests.swift`(git 제외됨)에만.
  커밋 전 `./scripts/check-pii.sh` 가 통과해야 한다(pre-commit 훅에도 걸려 있다).
- **하지 말 것**: 아키텍처 갈아엎기, 새 라이브러리 추가, 요청 안 한 리팩터링.
- **문서에 「확정」으로 적힌 세무 정책을 임의로 바꾸지 마라.** 이상하면 **질문으로 올려라.**
- **없는 결함을 만들지 마라.** 근거 없이 "의심스럽다"로 보고하지 마라.

## 6. 진행 방식

**① 조사 → 보고 → ② 계획 → 보고 → ③ 구현 → ④ 검증** 순으로,
각 단계마다 멈추고 보고하라. 발견 즉시 다 고치지 마라.

각 단계에서:
- 결함을 찾으면 **증상이 아니라 원인**을 고치고, **반드시 회귀 테스트를 하나 남겨라.**
  가능하면 "일부러 망가뜨리면 잡히는가"까지 확인하라.
- 골든값을 고칠 때는 **손계산 과정을 주석/커밋 메시지에 적어라.**
  설명이 안 되는 게 하나라도 나오면 **거기서 멈추고 보고하라.**
- 기록은 `docs/audit-<날짜>-<주제>.md` 에. 기존 감사 문서 형식을 따라라.
- 커밋은 승인 후에만. `main` 말고 브랜치에서.

## 7. 결함 보고 형식

각 건마다:

| 항목 | 내용 |
|---|---|
| **증상** | 쉬운 말로 무슨 일이 일어나는가 (전문용어는 괄호에) |
| **재현** | 최소 입력과 실행 방법. 가능하면 실패하는 테스트 코드 |
| **원인** | `file:line` + 왜 그렇게 되는가 |
| **영향 범위** | 세액이 커지는가 작아지는가, 누구에게 몇 %나 |
| **왜 기존 테스트가 못 잡았나** | ← **이 칸을 반드시 채워라.** 그물의 구멍이 어디인지가 결함 자체만큼 중요하다 |
| **고칠 방향** | 근본 원인 기준 |

마지막에 반드시 함께 보고하라:

> **확인했지만 문제 없던 범위** — 무엇을 **어떤 방법으로** 확인했는지.
> 이게 없으면 "안 본 것"과 "보고 괜찮았던 것"을 구분할 수 없다.

## 설계 근거 — 왜 이렇게 썼나

일반적인 "버그 찾아줘"와 갈리는 지점은 **1장과 2장**이다.

| 절 | 무엇을 막는가 |
|---|---|
| **1장 — 왜 기존 테스트를 믿으면 안 되는가** | AI 가 초록불을 안전 신호로 오해하는 것. 「결함 9건 중 8건이 전체 통과 상태에서 나왔다」는 실측을 주면 통계가 반박을 대신한다 |
| **2장 — 다섯 가지 무기** | "열심히 읽어 봤는데 괜찮아 보입니다"로 끝나는 것. 우회 방법을 **행동**으로 지정한다 — 법령 원문 · 구현 무관 성질 · 변이 · 실행 · 문서 대조. 전부 직전 회차에 실제로 결함을 잡은 경로다 |
| **무기 3 (변이 테스트)** | 그물 자체의 구멍. 「이 검사가 진짜 잡는가」를 확인하는 유일한 방법이라 빠지면 안 된다 |
| **4장 — 이미 알고 있는 미결** | 헛짚기. 법에 답이 없어 가정을 세운 자리를 미리 알려주지 않으면 "미결을 확정처럼 계산한다!"고 오보한다. 동시에 **진짜 결함의 경계**(고지 안 함 / 문서와 코드 불일치 / 미결을 확정 표시)를 명시했다 |
| **7장 「왜 기존 테스트가 못 잡았나」 칸** | 다음 회차의 재발. 결함 하나를 고치는 것보다 **그물의 구멍 위치를 아는 것**이 회차를 줄인다 |
